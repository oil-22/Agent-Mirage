# Jev 双截图验证集 v2.1

**验证集从 171 YES / 17 NO 扩到 171 YES / 76 NO。** 新增的 59 条全部来自历史 AndroidWorld 实验，覆盖 51 条轨迹、16 个任务族。前图、动作和候选图都属于同一历史事件，没有用其他事件的截图替换候选图。没有运行新交互、生成截图或训练模型。

| --- | ---: | ---: | ---: |
| [完整训练集](train.jsonl) | 1,655 | 2,185 | 3,840 |
| [新版验证集](val.jsonl) | 171 | 76 | 247 |
| [测试集](test.jsonl) | 417 | 14 | 431 |
| [可选平衡训练子集](train-balanced.jsonl) | 1,655 | 1,655 | 3,310 |

训练、平衡训练子集、测试、原生提示协议均与 v2 逐字节相同。完整训练集与平衡子集二选一。新版验证集的前 188 行就是[原验证集](val-v2-original.jsonl)，第 189–247 行是[仅新增的 59 条 NO](val-added-no.jsonl)；后者不应再拼接一次，也不能加入训练。所有 247 条验证样本都是实收对，离线构造为 0。

**NO 的依据是“第二张图不足以判断这次动作的可见结果”。** 任务本身失败不等于 NO：如果画面清楚显示了这次操作的失败提示，仍是 YES；能看清已经到达边界的滚动也可以是 YES。不能仅凭图像是否相同打标签。

正常交付 44 条、实验干预交付 15 条。这里的“正常”只指这一步的动作前后两次交付没有替换截图，不表示整次历史运行没有其他干预。25 条带对照的记录中，10 条的对照是同一轨迹紧接着重复执行该动作；对照图只用于复核，从来不是第三张模型输入图。对于 15 条干预样本，均有原生界面捕获摘要与实际交付摘要；其中 6 条还找到了未替换的原始 PNG。其余不以找不到的原图作视觉证据。

**查看实例。** 在[新增索引](val-added-index.jsonl)里用 `val_line` 找到对应输入行，或用 `sample_id` 查询[逐条回执](audit.jsonl)和[元数据](manifest.jsonl)：

- 第 204 行：点“新建联系人”后仍在联系人列表；同一轨迹再次点击才出现新建表单。本条输入的第二张图是第一次点击后收到的列表。
- 第 234 行：在桌面搜索输入 `phone`，收到的却是录音应用欢迎页。界面变化很大，但看不出这次输入的结果。
- 第 245 行：点击设置中的“应用”，第二张图进入“网络和互联网”。前图已高亮“网络和互联网”，该变化不能验证这一次点“应用”的结果。

**模型格式与复核。** 每行只有 `images`（动作前截图、实际交付的候选截图，按顺序）、`prompt`（含真实分发动作的完整英文提示）和大写 `label`。[protocol.json](protocol.json) 提供 system 文本、图片顺序和 A/B 到 YES/NO 的映射，审核理由不进入模型。新增记录由助手根据动作、图片和日志逐条复核；没有用 Jev 自己的打分选样或定标，也不代表多人独立标注。

解压后在目录内运行 `python verify.py`（Python 3.11+、Pillow）可离线检查原数据冻结、双图、动作、提示、回执绑定、对照图、去重和跨划分隔离；无需服务器或模型权重。[validation.json](validation.json) 是核验结果，[stats.json](stats.json) 是实际分布。使用项目原生判定头时，可从当前目录运行 `python native_head_v2.py check manifest.jsonl`。重建步骤和逐行审核决定见 [build/README.md](build/README.md)。

比较判定头与 LoRA 时，使用同一版验证集；除准确率外，分别报告 **NO 被判成 YES 的条数 / 76** 和 **YES 被判成 NO 的条数 / 171**。补充样本集中在 Android，这些比例不是线上发生率。需要与旧实验直接对比时，可单独评估保留的原 188 行；测试集仍只有 14 条 NO。
